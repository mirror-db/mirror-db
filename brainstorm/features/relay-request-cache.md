# Relay 请求缓存

## 目标

将哈希预判、上游探测、缓存交付和 MISS 写入串成统一请求链路，在流式交付的同时建立真实哈希存储。

## 非目标

- 不为 `X-MDB-Relay-No-Store` 响应建立普通缓存或域名分区缓存。
- 不在本功能中实现仓库元数据递归解析或自动 prefetch。

## 交互

1. **哈希预判**：从仓库元数据生成的资源—哈希映射寻找内容。
2. **哈希探测**：policy 允许时使用 HEAD，否则使用 GET 并在读取 body 前停止；从响应头取哈希，或以 identity 对照本地 identity-hash 表。
3. **缓存交付**：用上游 HEAD/GET 响应头拼装缓存 body；存储对象不存在或读取失败时回退上游。
4. **MISS**：获取上游 body，写 TMP_DIR，同时向客户端流式交付并计算 sha1/sha256，完成后按真实哈希提交存储。
5. **禁止缓存**：响应带 `X-MDB-Relay-No-Store` 时直接交付，不写 body、不建立 identity/hash 映射，也不进入 prefetch。

## 实现

- header 中的 MD5 与 ETag 用于资源 identity；讨论定义为 `identity = sha1(md5 + etag)`，具体编码与分隔规则待定。
- Release 等索引中的 MD5 被忽略，不作为内容身份依据。
- 内容新鲜度由哈希预判、探测和元数据更新负责；LRU 只负责容量回收。
- 响应开始向客户端传输后若缓存读取中断，不承诺无感重试。

## 验收

1. 四类请求路径均可独立判定：预判命中、探测命中、存储缺失回退、完整 MISS。
2. HEAD 不可用或被判为不支持时，能按 policy 改用 GET 探测。
3. MISS 只需一次上游 body 传输即可同时完成客户端交付、双哈希计算和存储提交。
4. 缓存命中使用当前上游响应头，不交付与当前身份不符的 body。
5. `X-MDB-Relay-No-Store` 响应不产生任何 relay 缓存写入。
